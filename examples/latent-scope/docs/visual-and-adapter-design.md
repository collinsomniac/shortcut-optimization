# A common instrument panel for two different model families

Research reviewed 24 September 2026. The attached Doom demonstration is a screenshot of a composed presentation. From the image alone we can distinguish a game viewport at bottom, action-score sliders on the right, heatmap-like tiles across the upper left, and a stylized Q/K/V attention path through summed and normalized operations. We cannot establish that the heatmaps are actual weights or activations, that the diagram shows the precise Jev architecture, or that each bright region causally produced an action. The caption reports 8.8 decisions/s *as played* and 12.1 ms per decision; those measure different scopes and are not arithmetic inverses.

The new Latent Scope panel applies the useful presentation idea while preserving evidence: a fixed-screen model-flow schematic above a **real** token-probability texture, a selected-step slider, a text-labeled candidate table with measured percentages, and the live prompt/reply panel. Green indicates input or output observed at a runtime/API boundary; subdued blue indicates an architectural stage whose tensor was not captured. The diagram does not animate individual weights.

| Stage | Current Llama/WebLLM | Future Laya browser adapter |
|---|---|---|
| Input | User prompt and chat context | State plus finite, labeled questions/criteria |
| Preparation | Time from request to first output, containing prefill plus overhead | Tokenization and encoder pass; *not* autoregressive prefill |
| Interior | Embedding → Q/K/V attention → residual/MLP shown schematically only | ModernBERT encoder plus option-marker/decision head shown schematically only |
| Observable score | Sampled next token, up to five returned rivals, and omitted mass | Per-question `choice`, `score`, or `noul` probabilities; calibration must be recorded |
| Output | Generated reply streamed across many token steps | Typed answers from a bounded decision step; no generated-token stream |
| Playback | Token index and elapsed time | Decision index and question ID; input/game state can advance independently |

**The same table and shader can show a distribution, but the units and meaning change.** For Llama, bars are vocabulary token probabilities at one decoding step. For Laya, each row is a named criterion in one typed question; a `score` may show level probabilities plus an expected score, while `noul` represents the probability of true. A score should never be presented as if it were a next-token probability. Model-specific adapters should output a discriminated `Frame` (`kind: 'next_token' | 'typed_choice' | 'typed_score' | 'typed_boolean'`) with `source`, `phase`, `labels`, `values`, `elapsedMs`, and an optional `modelRevision`. Panels change labels and explanatory text with the adapter; the layout stays stable. Memory-efficient switching means **one resident model at a time**, preserving the shared UI and cached model artifacts, not claiming zero-cost instantaneous swapping.

## GitHub research leads

The user's [shortcut-optimization repository](https://github.com/collinsomniac/shortcut-optimization) maps the iOS inference routes in [inference-routes](https://github.com/collinsomniac/shortcut-optimization/blob/main/docs/inference-routes.md) and [System-One decision models](https://github.com/collinsomniac/shortcut-optimization/blob/main/docs/research/system-one-decision-models.md). It recommends keeping a high-frequency game policy in one warm browser page and uses [CourierGrid](https://github.com/collinsomniac/shortcut-optimization/blob/main/docs/research/game-policy-benchmark.md) as a tractable browser game with explicit state/action contracts, an oracle and a progressive curriculum. That is a better first adapter demonstration than screenshot-driven Doom: policy errors and decision timing have ground truth.

The upstream [Laya model card](https://huggingface.co/convaiinnovations/laya) documents a 421M ModernBERT decision model, with a separate task-specialized checkpoint. The [official `laya-ts` README](https://github.com/NandhaKishorM/laya/blob/main/laya-ts/README.md) now describes split ONNX (`encoder.onnx` and `head.onnx`), browser WebGPU with WASM fallback, and telemetry hooks. It also describes export parity checking against PyTorch. These are credible implementation components. They do **not** mean that a 1.7 GB FP32 artifact will fit or perform well on an iPhone; we must first inspect a specific export, confirm artifact hashes and memory, and measure cold load and calibrated decisions on the target browser. The README's browser snippet is a capability description, not this app's tested integration. Laya's typed model and llama.cpp GGUF are different runtimes.

A second adapter would first run against an explicit local test fixture of typed decision frames in the CourierGrid page. Then it would load a pinned Laya ONNX export in a dedicated worker and map returned probabilities to the shared table. Worker message sizes should stay small: criteria, scores, timestamps and status, rather than hidden matrices. Where model outputs do not expose internal tensors, retain a schematic node. This preserves browser responsiveness and avoids fake activation maps. The game would show state → model → action → next state and an oracle comparison, while the LLM view remains prompt → prefill boundary → token candidates → reply.

## Responsive contract and verification

At normal mobile heights the page itself must stay within `100dvh`; the chat log alone may scroll. The scrub control sits between the probability texture and table, so the chat panel cannot cover it. At keyboard heights a compact layout prioritizes the composer, and **Focus diagram** reduces chat to its header. Verify on an iPhone 17 Pro Max: loaded/unloaded states, keyboard visible, 200% text enlargement, a 70+ token reply that evicts old columns, pin while new tokens arrive, return to live, pause/stop, graphics context restoration, orientation change, and exported trace parity. Measure display update work separately from inference throughput before claiming an optimization.
