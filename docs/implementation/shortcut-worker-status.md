### Failed/demoted routes

**SO-Copy-Actions / native action pasteboard:** demoted. The helper imported and
its Actions AppIntent resolved, but neither the original clipboard-staged run nor
the direct-text-input retry caused Paste/Paste Below to appear in the iOS 27
action context menu. It remains research material, not an installation backend.

**SO Library Manager Bootstrap / GenerateShortcutAction:** failed empirically.
The artifact was validly HubSign-signed, but iOS rejected import with
“contains features not supported on this device.” Do not use imported
`GenerateShortcutAction` as the automation substrate.

### Compiler/signing provenance

Earlier generic helpers such as `SO-Copy-Actions` were generated by this
repository's plist tooling and sent to the same HubSign endpoint. They were
**not compiled by Cherri**.

Cherri is now used as a pinned deterministic compiler for the direct persistent
controller. Signing still occurs only after compilation, normalization and
validation. The phone receives an already-signed AEA1 artifact.

## Persistent management pivot — 2026-09-25 UTC

The management architecture is now explicitly split:

- **persistent native library plane** — inventory/create/run/open/rename/move/folders/attributes/share/delete;
- **artifact/content plane** — snapshot/export/diff/edit/duplicate/install;
- **optional pasteboard transport** — local action-graph insertion experiment.

A v0.3-draft semantic protocol and [native capability catalog](../../harness/shortcuts/native-capabilities.json) are committed. The high-level operation `shortcuts.ensure(spec)` is intended to reuse an installed current Shortcut rather than regenerate it.

Apple's current first-party iOS 27 catalog exposes Create/Delete/Get/Set Attributes/Move/Open/Rename/Run/Create Folder/Create iCloud Link/Change Icon and related management intents. Apple's release notes independently document Create/Delete/Open Folder since iOS 16, Create Folder/Create iCloud Link since iOS 18.0, and Move/Rename since iOS 18.1.

No dedicated first-party Duplicate Shortcut AppIntent was found in the inspected iOS 27 catalog. Semantic duplication therefore belongs to the content plane: artifact clone first, action-pasteboard clone if verified, UI Duplicate only as fallback.

## Important correction: harness.info is not discovery

`harness.info` returns a **folder-scoped harness manifest**. The supplied export discovers the members of four fixed native folders; the dispatcher allowlist is a separate, uninspected mechanism.

Therefore:

- a Shortcut missing from `harness.info` may still exist on the phone;
- a direct RPC `tool_not_found` result means the dispatcher registry does not currently route that method name;
- earlier inference that “shortcuts.control is not installed because harness.info does not list it” was too strong.

Future architecture should make this registry source-controlled/dynamic or provide a dedicated discovery mechanism while retaining allowlist policy.

See [current harness architecture](../architecture/current-harness.md).

## Verified filesystem boundary

a-Shell cannot access the private Shortcuts SQLite store and its App Group does not contain the native Shortcuts collection.

Therefore:
- Shortcuts library folders are not filesystem folders;
- native inventory should use Get My Shortcuts;
- exported `.shortcut` artifacts should be copied deliberately into a worker Files/iCloud workspace for file-style inspection/versioning.

## Security status

Current direct privilege inspection shows:
- `anon` and `authenticated` have no SELECT/INSERT/UPDATE/DELETE privileges on the six inspected `shortcuts` tables;
- `service_role` has intended access;
- inspected Shortcut public RPC functions are executable by `service_role`, not `anon` or `authenticated`.

Five internal tables still have RLS disabled:
- inventory
- versions
- capability_snapshots
- receipts
- callbacks

Supabase flags this as defense-in-depth risk. Do not describe it as an active public data leak unless grants/exposed-schema configuration change. Review RLS intentionally before widening access.

## Current blocker, correctly stated

The blocker is **not** “the controller is absent because harness.info does not list it.”

The actual missing capability is:

> a reliable, programmatic path to discover, create, install, route, inspect, patch and verify Shortcut workflows without depending on a manually updated hardcoded dispatcher registry or an opaque natural-language builder step.

The user is explicitly comfortable making the Shortcuts app primarily agent-managed. That means future work can optimize around a dedicated harness/agent folder structure and a source-controlled registry rather than preserving unrelated personal Shortcuts.

## Highest-priority next implementation

1. Make the harness registry a first-class versioned artifact instead of hardcoded text.
2. Establish read-only native inventory with Get My Shortcuts.
3. Export one existing harness Shortcut and round-trip inspect it.
4. Programmatically patch the harness registry or `harness.info` itself.
5. Validate the patch on-device.
6. Only then expand semantic `shortcuts.*` management/generation methods.
7. Add structural `get/diff/edit` and version/hash conflict protection.

The target is not merely to “generate shortcuts”; it is to make the harness capable of improving its own Shortcut-based tool layer safely and reproducibly.
